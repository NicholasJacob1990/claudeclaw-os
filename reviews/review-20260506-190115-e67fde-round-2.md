## Summary

Round 2 does not contradict the Round 1 findings. The most important new issue is that the newly exposed Codex/Gemini CLI paths inherit the full parent environment, while the Claude SDK path already has a scrubber for exactly this threat model. I also found two runtime-safety issues in the War Room process-management and mixed-TTS routing paths, plus one contract gap where dashboard model settings do not take effect for non-Claude text agents.

## High Severity

### High - Non-Claude runtimes inherit unsanitized process environment

The Claude SDK path deliberately scrubs secret-shaped environment variables before spawning model-controlled tooling (`src/agent.ts:252-260`, `src/agent-voice-bridge.ts:88-93`, `src/security.ts:212-315`). The new/expanded non-Claude paths do not use that boundary. `runAgent` builds `cliSdkEnv = { ...process.env, ...cliEnv }` and passes it to `runNonClaudeRuntime` (`src/agent.ts:229-248`), and the voice bridge does the same for Codex/Gemini-backed agents (`src/agent-voice-bridge.ts:151-169`).

That gives Codex/Gemini subprocesses every secret in the parent process environment: dashboard token, DB encryption key, Slack/GitHub/Notion tokens, provider API keys, etc. This is worse than a normal API-call leak because these CLI runtimes are tool-capable; Gemini is launched with `--yolo` (`src/agent-runtimes.ts:137-143`) and Codex loads its configured tool/sandbox policy (`src/agent-runtimes.ts:120-127`). A prompt-injected task or voice-routed agent can ask the CLI to inspect `env` or write/exfiltrate secrets.

Action: introduce a CLI-specific scrubbed environment helper, pass only required auth variables (`OPENAI_API_KEY`, `GEMINI_API_KEY`, `GOOGLE_API_KEY` as appropriate), and add regression tests that prove secret-shaped variables are absent from both `runAgent` and `agent-voice-bridge` non-Claude spawns.

## Medium Severity

### Medium - Mixed TTS silently routes speech to a different provider than the configured per-agent provider

In mixed mode, `ClaudeAgentBridge` sends the selected per-agent provider via `TTSUpdateSettingsFrame` (`warroom/agent_bridge.py:116-155`). But `MixedProviderTTSService._select_provider()` treats that explicit provider as only the first candidate, then falls through to `WARROOM_MIXED_DEFAULT_PROVIDER`, `xai`, `elevenlabs`, `voxtral`, and `groq` if the selected provider is not ready (`warroom/server.py:1712-1742`). The only signal is a warning log (`warroom/server.py:1756-1758`).

That breaks the user-facing contract of per-agent provider selection. If an agent is pinned to ElevenLabs but the voice id is missing, the same text can be sent to xAI, Mistral, or Groq instead. This is a privacy/cost/compliance issue, not just a voice-quality fallback, because the selected provider is effectively ignored.

Action: distinguish explicit provider selection from auto/default mode. If `voices.json` sets `audio_provider`, fail that response with a visible TTS error when the provider is unavailable. Only use fallback order when no explicit provider was selected.

### Medium - War Room port cleanup can kill unrelated local services

The new stale-port cleanup kills every PID listening on `WARROOM_PORT` before spawning the War Room process (`src/index.ts:270-276`). The dashboard respawn path also unions `findProcessesByPattern('warroom/server.py')` with every PID listening on the port and kills all of them (`src/dashboard.ts:744-749`). `findListeningPidsByPort()` returns raw PIDs from `lsof`/`netstat` without command-line validation (`src/platform.ts:64-91`).

If `WARROOM_PORT` collides with another developer service, or is accidentally configured to a shared/critical port, this code terminates the unrelated listener. That creates a local denial-of-service footgun and makes dashboard actions more destructive than their label suggests.

Action: only kill listener PIDs whose command line matches the managed War Room server, or a PID that this process spawned and still tracks. If the port is occupied by anything else, return a clear conflict error instead of killing it.

### Medium - Dashboard model changes are ignored for non-Claude sub-agents in the text runtime path

The dashboard persists per-agent model changes into `agent.yaml` and reports `restartRequired: true` (`src/dashboard.ts:2255-2288`). `loadAgentConfig()` exposes that model as `cfg.model` (`src/agent-config.ts:97-166`). The voice bridge reads and forwards it for non-Claude agents (`src/agent-voice-bridge.ts:121-160`), but the normal text path does not: for non-main agents, `runAgent()` only copies `cfg.runtime` and leaves `resolvedModel` unchanged (`src/agent.ts:220-240`).

Result: a Codex/Gemini sub-agent can show the dashboard-selected model while the actual CLI invocation uses the CLI default. This creates divergent behavior between Telegram/text and voice War Room, and makes model rollback/pinning unreliable.

Action: when loading a non-main agent config, set `resolvedModel = cfg.model` unless the caller provided an explicit model. Validate that the model prefix is compatible with the selected runtime before adding `--model`.

## Low Severity

### Low - Dashboard readiness probe relies on undeclared `ws` dependency

`probeWarRoomWebSocket()` dynamically imports `ws` (`src/dashboard.ts:580-582`), but `package.json` does not list `ws` as a direct dependency. It is currently present through transitive dependencies in `package-lock.json`, which is brittle for production/pruned installs. If the transitive dependency changes, `/api/warroom/start` will fail readiness probing even though the Python server is healthy.

Action: add `ws` to direct dependencies, or replace the probe with a built-in Node WebSocket implementation if the supported Node runtime provides one.

## Positive Observations

- The new team-mode tool timeout calculation accounts for multi-agent calls instead of reusing the single-agent ceiling.
- The bridge payload parser now tolerates CLI stdout noise by scanning from the bottom for a JSON object.
- The frontend normalizes `router` to `auto`, preserving a backward-compatible server mode while keeping one active UI button.
- `agent-voice-bridge` now uses the shared agent config resolver, which reduces drift for custom agents outside `PROJECT_ROOT/agents`.
