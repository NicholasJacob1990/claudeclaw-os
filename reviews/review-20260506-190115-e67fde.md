# Round 1

## Summary

Round 1 found one high-severity security issue and two medium-severity runtime/contract issues in the proposed War Room/runtime changes. `npm run typecheck` and `python3 -m py_compile warroom/server.py warroom/agent_bridge.py warroom/personas.py` pass, so the risk is not syntax-level; it is in what the new dashboard fields and provider modes allow at runtime.

## High Severity

### High - Voxtral reference-audio path can exfiltrate arbitrary local files

The dashboard accepts `voxtral_ref_audio_path` as any string and persists it directly to `warroom/voices.json` (`src/dashboard.ts:1599-1604`). The Python War Room then opens that path and base64-encodes the bytes for the Mistral/Voxtral request (`warroom/server.py:1487-1493`, `warroom/server.py:1647-1653`, then used at `warroom/server.py:1871-1874`).

This turns a voice config field into a local-file read plus outbound upload primitive. A token holder, compromised dashboard session, or prompt-injected agent that can modify the config can point it at `.env`, SSH keys, local tokens, database files, etc. The file contents are then sent to an external provider as `ref_audio`. File extension and contents are not checked; the code only catches `OSError`.

Action: only allow reference audio from a dedicated safe directory such as `warroom/ref-audio` or a configured `WARROOM_REF_AUDIO_ROOT`, require realpath containment, reject symlinks, validate extension and max size, and reject unknown agent ids on `/api/warroom/voices`.

## Medium Severity

### Medium - Main runtime override can silently no-op or pass an incompatible model to a CLI

`PATCH /api/agents/main/runtime` always returns `{ ok: true }` after calling `setMainRuntimeOverride` (`src/dashboard.ts:2196-2205`), but `setMainRuntimeOverride` only writes when `ALLOWED_CHAT_ID` is set (`src/bot.ts:184-185`). If `ALLOWED_CHAT_ID` is absent, the endpoint reports success and nothing changes.

There is also a model/runtime mismatch path. The runtime override is independent from `chatModelOverride`; `runAgent` forwards any resolved model to the selected CLI as `--model` (`src/agent.ts:229-240`). If the chat previously selected `gpt-5.5` and the dashboard then forces `gemini`, the Gemini CLI receives `--model gpt-5.5`. The inverse is also possible. That produces confusing runtime failures after an apparently successful dashboard change.

Action: make the setter return whether it actually wrote state, and clear or reject incompatible existing model overrides when the runtime changes.

### Medium - New War Room providers are exposed without the matching Python dependency contract

The UI/API now expose `elevenlabs`, `voxtral`, and `mixed` providers, and `mixed` can call `aiohttp`, `groq.AsyncGroq`, `mistralai`, and Pipecat Groq/ElevenLabs/xAI service modules. The pinned provider is accepted by the dashboard, but `warroom/requirements.txt:1-2` still installs only `pipecat-ai[websocket,deepgram,cartesia,silero]` and `python-dotenv`.

That makes the new provider options fail only after the server respawns and imports the selected path. `voxtral` has an explicit runtime error for missing `mistralai` (`warroom/server.py:1460-1465`), but `mixed` and `groq` paths can still fail later from missing SDKs or Pipecat extras. The dashboard contract test only verifies that `mixed` is accepted, not that the configured environment can actually start it.

Action: update `warroom/requirements.txt` and add a startup/provider readiness check that fails `/api/warroom/provider` or `/api/warroom/start` with a clear dependency error before killing the running server.

## Low Severity

### Low - Groq per-agent voice selection is advertised but not wired

The per-agent UI allows `audio_provider: "groq"` (`src/dashboard.ts:1557-1559` and the Voices UI), and `ClaudeAgentBridge` maps Groq to `groq_voice` (`warroom/agent_bridge.py:33-40`). However `/api/warroom/voices`, `warroom/voices.json`, and both Voices UIs do not expose or persist `groq_voice`. Selecting Groq per agent therefore falls back to `WARROOM_GROQ_VOICE`/`autumn` and cannot actually be configured per agent.

Action: either add `groq_voice` end-to-end or remove Groq from the per-agent provider selector until it is configurable.

## Positive Observations

- The WebSocket readiness probe is stricter than a TCP probe and addresses a real startup race.
- `_run_subprocess` now kills the whole process group on timeout, which prevents orphaned CLI children after voice-turn timeouts.
- The voice bridge now uses the same `resolveAgentDir`/`loadAgentConfig` source of truth as other surfaces, reducing config drift for custom agents.
- The new bridge JSON parser is more tolerant of extra stdout before the final payload.

# Round 2

## Summary

Round 2 does not contradict the Round 1 findings. The most important new issue is that the newly exposed Codex/Gemini CLI paths inherit the full parent environment, while the Claude SDK path already has a scrubber for exactly this threat model. I also found two runtime-safety issues in the War Room process-management and mixed-TTS routing paths, plus one contract gap where dashboard model settings do not take effect for non-Claude text agents.

## High Severity

### High - Non-Claude runtimes inherit unsanitized process environment

The Claude SDK path deliberately scrubs secret-shaped environment variables before spawning model-controlled tooling (`src/agent.ts:252-260`, `src/agent-voice-bridge.ts:88-93`, `src/security.ts:212-315`). The new/expanded non-Claude paths do not use that boundary. `runAgent` builds `cliSdkEnv = { ...process.env, ...cliEnv }` and passes it to `runNonClaudeRuntime` (`src/agent.ts:229-248`), and the voice bridge does the same for Codex/Gemini-backed agents (`src/agent-voice-bridge.ts:151-169`).

That gives Codex/Gemini subprocesses every secret in the parent process environment: dashboard token, DB encryption key, Slack/GitHub/Notion tokens, provider API keys, etc. This is worse than a normal API-call leak because these CLI runtimes are tool-capable; Gemini is launched with `--yolo` (`src/agent-runtimes.ts:137-143`) and Codex loads its configured tool/sandbox policy (`src/agent-runtimes.ts:120-127`). A prompt-injected task or voice-routed agent can ask the CLI to inspect `env` or write/exfiltrate secrets.

Action: introduce a CLI-specific scrubbed environment helper, pass only required auth variables (`OPENAI_API_KEY`, `GEMINI_API_KEY`, `GOOGLE_API_KEY` as appropriate), and add regression tests that prove secret-shaped variables are absent from both `runAgent` and `agent-voice-bridge` non-Claude spawns.

## Medium Severity

### Medium - Mixed TTS silently routes speech to a different provider than the configured per-agent provider

In mixed mode, `ClaudeAgentBridge` sends the selected per-agent provider via `TTSUpdateSettingsFrame` (`warroom/agent_bridge.py:116-155`). But `MixedProviderTTSService._select_provider()` treats that explicit provider as only the first candidate, then falls through to `WARROOM_MIXED_DEFAULT_PROVIDER`, `xai`, `elevenlabs`, `voxtral`, and `groq` if the selected provider is not ready (`warroom/server.py:1712-1742`). The only signal is a warning log (`warroom/server.py:1756-1758`).

That breaks the user-facing contract of per-agent provider selection. If an agent is pinned to ElevenLabs but the voice id is missing, the same text can be sent to xAI, Mistral, or Groq instead. This is a privacy/cost/compliance issue, not just a voice-quality fallback, because the selected provider is effectively ignored.

Action: distinguish explicit provider selection from auto/default mode. If `voices.json` sets `audio_provider`, fail that response with a visible TTS error when the provider is unavailable. Only use fallback order when no explicit provider was selected.

### Medium - War Room port cleanup can kill unrelated local services

The new stale-port cleanup kills every PID listening on `WARROOM_PORT` before spawning the War Room process (`src/index.ts:270-276`). The dashboard respawn path also unions `findProcessesByPattern('warroom/server.py')` with every PID listening on the port and kills all of them (`src/dashboard.ts:744-749`). `findListeningPidsByPort()` returns raw PIDs from `lsof`/`netstat` without command-line validation (`src/platform.ts:64-91`).

If `WARROOM_PORT` collides with another developer service, or is accidentally configured to a shared/critical port, this code terminates the unrelated listener. That creates a local denial-of-service footgun and makes dashboard actions more destructive than their label suggests.

Action: only kill listener PIDs whose command line matches the managed War Room server, or a PID that this process spawned and still tracks. If the port is occupied by anything else, return a clear conflict error instead of killing it.

### Medium - Dashboard model changes are ignored for non-Claude sub-agents in the text runtime path

The dashboard persists per-agent model changes into `agent.yaml` and reports `restartRequired: true` (`src/dashboard.ts:2255-2288`). `loadAgentConfig()` exposes that model as `cfg.model` (`src/agent-config.ts:97-166`). The voice bridge reads and forwards it for non-Claude agents (`src/agent-voice-bridge.ts:121-160`), but the normal text path does not: for non-main agents, `runAgent()` only copies `cfg.runtime` and leaves `resolvedModel` unchanged (`src/agent.ts:220-240`).

Result: a Codex/Gemini sub-agent can show the dashboard-selected model while the actual CLI invocation uses the CLI default. This creates divergent behavior between Telegram/text and voice War Room, and makes model rollback/pinning unreliable.

Action: when loading a non-main agent config, set `resolvedModel = cfg.model` unless the caller provided an explicit model. Validate that the model prefix is compatible with the selected runtime before adding `--model`.

## Low Severity

### Low - Dashboard readiness probe relies on undeclared `ws` dependency

`probeWarRoomWebSocket()` dynamically imports `ws` (`src/dashboard.ts:580-582`), but `package.json` does not list `ws` as a direct dependency. It is currently present through transitive dependencies in `package-lock.json`, which is brittle for production/pruned installs. If the transitive dependency changes, `/api/warroom/start` will fail readiness probing even though the Python server is healthy.

Action: add `ws` to direct dependencies, or replace the probe with a built-in Node WebSocket implementation if the supported Node runtime provides one.

## Positive Observations

- The new team-mode tool timeout calculation accounts for multi-agent calls instead of reusing the single-agent ceiling.
- The bridge payload parser now tolerates CLI stdout noise by scanning from the bottom for a JSON object.
- The frontend normalizes `router` to `auto`, preserving a backward-compatible server mode while keeping one active UI button.
- `agent-voice-bridge` now uses the shared agent config resolver, which reduces drift for custom agents outside `PROJECT_ROOT/agents`.

# Round 3

## Summary

Round 3 does not retract the Round 1 or Round 2 findings. I found two additional medium-severity contract issues in the attempted fixes/new surface area: model selection is still not consistently applied across dashboard/main and SDK runtime paths, and the new voice team modes are accepted globally even when the selected audio stack cannot execute them.

## High Severity

No new high-severity findings in this round beyond the unresolved high-severity issues already raised in prior rounds.

## Medium Severity

### Medium - Model/runtime override plumbing is still inconsistent across dashboard main and SDK runtimes

The Round 2 model-propagation issue is only partially addressed. The new `runAgent()` logic resolves `resolvedModel` for main from `getMainModelOverride()` only when the caller did not already pass a model (`src/agent.ts:211-218`). But dashboard chat always calls `runAgent(..., agentDefaultModel, ...)` (`src/bot.ts:1710-1719`), so a dashboard-set main override such as `gpt-5.5` is masked by the default Claude model. If the dashboard also set main runtime to `codex`, the Codex CLI receives `--model <claude default>` from `src/agent.ts:239-248`.

There is a second related gap for SDK runtimes. `runAgent()` forwards the selected model only through `cliFlags` (`src/agent.ts:239-248`), while `runOpenAISdkRuntime()` and `runGeminiSdkRuntime()` ignore those flags and read only `OPENAI_DEFAULT_MODEL` / `GEMINI_DEFAULT_MODEL` (`src/agent-runtimes.ts:264-280`, and the OpenAI SDK path has the same pattern). So dashboard model settings still do not reliably control `openai-sdk` / `gemini-sdk` agents even though the dashboard exposes those runtimes.

Impact: the UI can report a model/runtime combination that is not what executes. In the worst common path, dashboard main can route to Codex/Gemini with an incompatible Claude model id and fail after an apparently successful configuration change.

Action: make model an explicit runtime input, prefer per-chat/dashboard overrides over process defaults for main, load `cfg.model` for non-main agents when no explicit caller model exists, and have both SDK adapters consume `input.model`. Validate model/runtime compatibility before spawning or calling SDKs.

### Medium - Team/single voice modes are accepted for audio stacks that ignore them

The UI/API now allow `single`, `broadcast`, `debate`, `ensemble`, and `consensus` in `/api/warroom/pin` (`src/dashboard.ts:711-787`) and the War Room UI presents them as real modes (`src/warroom-html.ts:758-838`, `web/src/pages/WarRoom.tsx:17-32`). Those modes are implemented only in `run_live_mode()` through Gemini Live tool registration (`warroom/server.py:934-1055`).

The non-live provider paths still build `Groq/Deepgram/Voxtral STT -> AgentRouter -> ClaudeAgentBridge -> TTS` pipelines. `run_mixed_mode()` is the newest example (`warroom/server.py:1939-1972`): it never reads `active_mode`, never registers `answer_team`, and its `AgentRouter` only emits `"single"` or `"broadcast"` based on spoken trigger words, not the pinned mode (`warroom/router.py:132-264`). The same shape applies to the stitched `groq`, `cartesia`, `elevenlabs`, and `voxtral` paths.

Impact: users can select “Consensus” or “Debate” while the provider pin is `mixed`, `groq`, `elevenlabs`, `voxtral`, or `cartesia`; the backend accepts the mode but the running server treats the next utterance as a normal pinned/prefix-routed single-agent turn. That is a silent product-contract failure and can route prompts to fewer agents than the UI claims.

Action: either implement mode-aware routing in the non-live stacks, or reject/disable modes that require Gemini Live when the pinned provider is not `gemini-live` / `gemini-live-25`. A clear 400 from `/api/warroom/pin` is preferable to silently ignoring the selected mode.

## Low Severity

### Low - Voxtral env names are inconsistent between `.env.example` and Telegram TTS fallback

`.env.example` documents `WARROOM_VOXTRAL_TTS_MODEL`, `WARROOM_VOXTRAL_VOICE_ID`, and `WARROOM_VOXTRAL_REF_AUDIO_PATH`, but the Telegram TTS cascade in `src/voice.ts` reads `VOXTRAL_TTS_MODEL`, `VOXTRAL_VOICE`, and `VOXTRAL_REF_AUDIO`. War Room and Telegram voice therefore use different variable names for the same provider, and a user following the documented example will not configure the new Telegram fallback as expected.

Action: accept the documented `WARROOM_VOXTRAL_*` names as aliases in `src/voice.ts`, or document separate non-War-Room variables explicitly.

## Positive Observations

- The Gemini CLI headless invocation is consistent with the installed CLI help: `-p/--prompt` switches to headless mode and appends stdin.
- The Codex CLI change to `codex exec --skip-git-repo-check` matches the installed CLI contract and removes dependency on the project being a Git repository.
- The new `answer_team` timeout calculation is directionally right for multi-agent voice calls; it accounts for participant count instead of reusing a single-agent ceiling.
- The front-end mode normalization from `router` to `auto` keeps backwards compatibility while avoiding duplicate active buttons.
